## Этап 1. Папки открываются сразу: повторно и после перезапуска

**Для пользователя.**
- «Назад» и возврат в папку — содержимое сразу, сверка с облаком тихо в фоне.
- Перезапуск — список с устройства сразу после проверки доступа, без ожидания чтения папки.
- Двойной клик по папке на доске откликается так же, как клик в дереве.

**Как сейчас.** `navigate_open_folder` всегда ждёт сеть и только потом меняет папку
(`apps/client/src/store/createWorkspaceStore.ts:936-950`), даже если папка уже лежит в
`store.folders`. Подписка свежая только у открытой папки и её потомков
(`createWorkspaceStore.ts:610-614`, `packages/file-manager/src/supabase.ts:1718-1719`):
корень, пока открыта подпапка, в `store.folders` устаревает. Двойной клик по папке на
доске идёт в `store.open` (`createWorkspaceStore.ts:2650`), ждёт сеть, и навигация
подхватывает папку уже после смены (`ui/explorer/FolderContent.vue:51-55`).

**Что меняем.**
- **Показ из памяти.** Папка уже в `store.folders` — `navigate_open_folder` показывает её
  сразу. Свежесть даёт перечитывание, не подписка: сразу после показа — фоновая сверка
  через `refresh_cached_folder`. Он берёт номер чтения (`store/helpers/refreshCachedFolder.ts:34-50`),
  заново накладывает незаконченный вид (`:174`) и не сбрасывает выделение. Повторный
  `navigate_open_folder` для сверки не годится: он в начале сбрасывает выделение
  (`createWorkspaceStore.ts:934`).
- **Сверка только читает.** На событии изменения содержимого `refresh_cached_folder`
  возвращает файлам атрибуты, потерянные при сохранении в другом редакторе, и пишет их в
  облако `fm.set_xattrs` (`restore_layout_lost_on_save`, `refreshCachedFolder.ts:94-110`,
  `:174-175`). Для сверки после навигации это опасно: она вернула бы атрибут, который
  другое устройство удалило. Сверка идёт отдельным режимом без этой записи (не как
  событие `modify`). Тест: атрибут удалён с другого устройства → переход в папку →
  сверка его не возвращает ни на экран, ни в облако.
- **Кеш списков на устройстве.** IndexedDB, ключ — пользователь + воркспейс + папка, лимит
  по числу папок, давно не открытые уходят первыми.
  - Пишем **неизменяемый снимок** ответа сети в том виде, в каком его собирает
    файл-менеджер (`.pile` уже вырезан, `supabase.ts:1547-1554`), снятый **до** любого
    наложения: тот же объект потом меняется на месте (незаконченный вид, восстановленные
    атрибуты). На диск попадает только то, что подтвердило облако.
  - Сеть не ждёт диска. Чтение папки стартует сразу, как сейчас
    (`store/helpers/openWorkspaceStore.ts:22-29`); ответ диска ограничен по времени, как у
    картинок (`services/workspace/pileImageCache.ts:151-156`). Ответ сети всегда
    применяется поверх диска (номер чтения).
  - **При запуске проверку доступа не обходим.** Стор открывается только после
    `get_workspace_access` (`openWorkspaceStore.ts:74-97`, `supabase.ts:1867-1883`): запуск
    в облачную папку покажет список с устройства после проверки доступа, без ожидания
    чтения папки. «Назад» и повторный вход внутри сеанса доступ не проверяют — там сразу.
  - **Запись после стирания невозможна.** Нынешняя эпоха этого не гарантирует:
    `seed_pile_url` пишет на диск без проверки эпохи, а сброс не ждёт `disk.clear`
    (`pileImageCache.ts:132-136`, `:195-197`), так что старая запись может закончиться уже
    после выхода. Для списков (в них имена файлов) запись и стирание идут одной очередью:
    стирание ждёт начатые записи, запись проверяет эпоху внутри очереди. Тот же порядок —
    для картинок в `pileImageCache.ts`. Тест гонки: запись начата → выход → запись
    закончилась → на диске пусто.
- **Пометка «обновляется»** в шапке, пока показ из памяти или с диска не сверен.
  Едва заметная; вид — по живому варианту.
- **Двойной клик** по папке на доске идёт через `explorer_navigation.open_folder`, как
  дерево (`ui/explorer/sidebar/TreeRow.vue:246`). Тогда цель ставится до чтения
  (`store/explorer/navigation.ts:277-278`), и `FolderContent` по ней сразу прячет старую
  папку (`FolderContent.vue:28`) — та же заготовка 1a.

Файлы: `store/createWorkspaceStore.ts`, `store/helpers/refreshCachedFolder.ts`,
`store/helpers/openWorkspaceStore.ts`, `services/workspace/pileImageCache.ts` (эпоха),
новый `services/cloud/folderListDisk.ts`, обработчик двойного клика на доске.

**Замер.** «Назад» в корень открытого стора; повторный вход в подпапку; запуск в облачную
папку (перезагрузка) — отдельно проверка доступа и показ; двойной клик по папке на доске.

**Риски.**
- До сверки виден устаревший список (папку удалили с другого устройства). Действие над
  исчезнувшей строкой даёт понятную ошибку, а сверка через ~0,5 с приводит экран к облаку.
- Имена файлов лежат на диске. Стираются при выходе, как обложки.
- Выделение и история не сбиваются, когда сверка подменяет список: если строки на месте,
  выделение остаётся.

**База и бэкенд:** нет, только клиент.

## Этап 2. Лёгкие картинки в плитках

**Для пользователя.**
- Доска с фотографиями открывается за секунды, а не качает оригиналы.
- После перезапуска плитки на месте сразу.
- Оригинал — при открытии на весь экран, скачивании, экспорте, синке и AI, как сейчас.

**Что меняем.**
- **База (forward diff, одна функция).** `list_pending_derivatives` без условия
  `w.is_public` (`rpc.sql:2074`): воркер берёт картинки и видео всех воркспейсов. Уже
  залитое подхватит сам, по одному блобу (`apps/backend/src/derivatives.ts:15-17`).
  Вместе с этим меняются проверки «приватная доска не попадает в очередь»
  (`rls.test.sql:753`, `:1225`). Новая версия `download_target` не нужна.
- **Бэкенд.** `GET /presign` принимает просьбу плитки `preview=1`. `choose_download`
  (`blobs.ts:166-187`): участнику с этой просьбой — готовое превью (картинке `thumb`,
  видео `poster`), иначе оригинал. Без просьбы участник получает оригинал, как сейчас:
  иначе `read_entry_blob` откажется копировать не-оригинал
  (`apps/client/src/services/workspace/entryBytes.ts:31-34`). Чужим — как сейчас. Что
  отдано, ответ уже говорит (`blobs.ts:323-325`). Старый бэкенд незнакомый параметр
  игнорирует и отдаёт оригинал.
- **Клиент.**
  - Превью — режим `useMediaSrc` по умолчанию (`ui/workspace/folder-container/media/useMediaSrc.ts:55-62`).
    Через него идут все плитки: `MasonryImage.vue:10`, `MediaPreviewShell.vue:14`, файл в
    `ItemTile.vue:38`, `LayerGlyph.vue:22-25`. Оригинал — явно там, где он нужен:
    `ModelPreviewShell.vue` (у 3D-моделей превью нет) и просмотр на весь экран, если он
    идёт через `useMediaSrc` (уточнить при реализации). AI (`services/ai/imageInput.ts`)
    и копирование (`crossStoreTransfer.ts`) зовут `store.get_media_src` напрямую — там
    оригинал, как сейчас. `store.get_media_src` (`createWorkspaceStore.ts:1885-1886`)
    передаёт просьбу дальше в файл-менеджер. Постер у видео уже рисуется картинкой, ролик
    не монтируется (`previewElement.ts:12-15`).
  - Ключ `mediaSrcCache` включает вариант: сейчас кеш один на id файла
    (`mediaSrcCache.ts:38-42`). Оригинал, показанный, пока превью нет, в ячейку превью
    не кладём.
  - Обложки и фоны (`useResolvedFill.ts:77`) — другой путь: pile-файл до 2048 px
    (`choosePileImage.ts:14`). Граница «ширина места × DPR» выбирает между готовым
    превью 1600 px и самим файлом.
- **Кеш на устройстве.** Превью картинок-файлов и постеры кладутся на устройство, как
  обложки. Кеш ссылок `mediaSrcCache` переезжает со стора на воркспейс и переживает смену
  корня. Контракт ключа:
  - нужна версия содержимого. В списке папки её нет (у строки только путь, имя, тип и
    атрибуты, `supabase.ts:1547-1559`), в `MediaSrc` нет `storage_key`
    (`packages/file-manager/src/types.ts:40-51`);
  - чтобы с диска показывать без `presign`, версия должна прийти со списком: добавить в
    строку папки `storage_key` или `content_modified_at` из `folder_read` (что можно
    отдавать гостю публичной доски — сверить с `SECURITY.md`). Ключ — версия + вариант;
    новые байты — новая версия, кеш не устаревает;
  - если версию в список не добавлять — ключ из ответа `presign`, и диск экономит только
    скачивание, не запрос;
  - кеш хранит MIME вместе с байтами: сейчас Blob всегда `image/webp`
    (`pileImageCache.ts:82-86`), а постер — `jpeg`.
- **Размер превью.** Существующий: 1600 px webp (`DERIV_IMAGE_EDGE`). Меньший вид для
  плиток (он же «меньшая обложка» из прошлого «Позже») — новый вид превью и ещё одна правка
  схемы; на потом, по замеру.

**Замер.** Тестовая облачная папка с 20–30 фотографиями по 2–5 МБ: сколько МБ скачано и
время до всех плиток; то же после перезагрузки.

**Риски.**
- Превью ещё нет (картинку только что залили) — плитка показывает оригинал, как сейчас.
- Цена догона: запрос очереди каждый раз группирует все подходящие блобы и только потом
  режет лимитом (`rpc.sql:2051-2052`, `:2087-2088`). Со всеми воркспейсами он тяжелее;
  оценить по объёму, при необходимости — индекс или предварительный фильтр.
- Квота превью не считает (`schema.sql:2210-2212`, `rls.test.sql:1299-1304`); HEIC и
  прочие неподдерживаемые форматы остаются оригиналом (`derivatives.ts:86-92`) — так уже
  сейчас.

**База:** да, `create or replace` одной функции: `postgres.test.ts` до, применение с
согласия пользователя, `test:rls:remote` после. **Порядок:** база → бэкенд → клиент.

## Этап 4. Хвосты вида и обложек

**Для пользователя.**
- Новый вид папки виден и на закрытом корне в дереве, и в публикации того же воркспейса.
- Десктоп и выход из аккаунта не теряют молча незалитую обложку или вид.
- Старые обложки чистятся одним запросом и без гонок между устройствами.

**Что меняем.**
- **Ожидающий вид на закрытом корне и во втором сторе.** Дерево закрытого корня берёт
  `DriveRoot.view` из `cloud_roots()` (`TreeRow.vue:134-137`, `store/explorer/drives.ts:448-453`).
  `note_cloud_root_look` обновляет только плитку страницы «Облако» и только для `/`
  (`createWorkspaceStore.ts:196`, `CloudPage.vue:27-35`). Второй стор того же id (облако и
  публикация) при открытии ожидающее не накладывает — это делают только
  `refresh_cached_folder` (`refreshCachedFolder.ts:174`) и `reload_folder_cache`
  (`createWorkspaceStore.ts:1714-1715`). Накладываем во всех трёх местах.
- **Подтверждение закрытия окна и выхода.** В вебе уже есть `beforeunload` на
  `has_unsaved_writes` (`ui/app/AppShell.vue:111-116`); счётчик уже держит и заливку, и
  запись вида (`choosePileImage.ts:129`, `xattrs.ts:460`). Добавляем `onCloseRequested`
  в десктопе и проверку в `sign_out` (`store/cloud.ts:526-531`). Если всё же вышли —
  фоновые записи отменяются, ошибка показывается глобально.
- **Чистка картинок на сервере одной операцией.** RPC вместо цикла «прочитать `.pile` →
  удалить по одному» (`supabase.ts:1291-1338`). Порог прежний: файл свежий, если
  `updated_at` папки минус `updated_at` файла меньше часа (`supabase.ts:1317-1325`) —
  теперь по заблокированной строке папки. Блокировки в порядке удаления: воркспейс, затем
  строки (`schema.sql:1608-1629`); `merge_entry_xattrs` блокировку воркспейса не берёт
  (`rpc.sql:101-175`). Со старой базой клиент идёт прежним путём.
- **Чистка против «освежения».** Повторный выбор старой обложки освежает файл через
  `merge_xattrs`, а ответ `missing` сейчас игнорируется (`supabase.ts:1219-1226`). Если
  чистка удалила файл прямо перед этим, токен укажет на отсутствующий файл. Одной RPC
  мало, нужны обе стороны:
  - чистка удаляет файл одним `UPDATE`/`DELETE` с условием свежести в `WHERE` по самой
    строке файла. Если «освежение» закоммитилось раньше, при повторной проверке строка
    уже свежая и остаётся;
  - «освежение» с ответом `missing` — не успех: файл заливается заново (байты на
    устройстве), и только потом пишется токен.

  Тест в `postgres.test.ts` на двух соединениях: чистка против «освежения» с последующей
  записью токена. Исход — либо файл жив, либо «освежение» получило `missing`; токена на
  отсутствующий файл не бывает.

**Снято после ревью 1:** отдельный слой показа для токена обложки на время заливки.
Причина в прошлом плане неверна: `copy_entry` и `list_xattrs` читают сервер
(`rpc.sql:429-431`, `:473-499`, `supabase.ts:1542-1544`; копирование между сторами тоже
берёт `list_xattrs`, `crossStoreTransfer.ts:292-308`), а на сервер токен попадает только
после заливки (`xattrs.ts:471-480`). Токен живёт в представлениях в памяти
(`createWorkspaceStore.ts:192-213`) — для показа это безопасно. Условие: на диск (этап 1)
