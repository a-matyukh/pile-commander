# План: облако ощущается как локальная папка

Ветка `perf/cloud-speed` от 2.6.0. Это итоговое состояние плана перед очередным ревью:
сначала Cursor, потом Kimi; замечания приходят сообщением, план обновляется по ним.
Продуктовая часть (решения, замеры, выбор хранилища) — в репо `pile-commander-product`,
папка «Скорость облака».

## Цель и правила

Облачная папка ощущается так же быстро, как локальная. Сеть быстрее не станет: запрос
стоит 0,3–1 с, у нас цепочки из 4–10 запросов. Поэтому главный принцип — **не ждать сеть**:

1. Действие пользователя видно сразу. Сеть догоняет в фоне.
2. Если фон не удался — понятная ошибка и откат к тому, что лежит в облаке.
   Никаких молча «висящих» изменений.
3. То, что уже видели, показывается из кеша без сети.
4. Только потом — сокращать сами цепочки запросов.

Границы:
- Прод Supabase: схему меняет только этап A (`create or replace` одной функции,
  forward diff по `AGENTS.md`, применение — с отдельным согласием пользователя).
  Остальные этапы схему не трогают.
- Порядок записи в облако не меняется там, где от него зависят другие устройства
  (сначала файл картинки, потом атрибут со ссылкой на него).
- Выбор хранилища (B2 / R2 / Wasabi / CDN) в этот план не входит — решаем после замеров.
- Без ожидания делаем только то, что перечислено. Позиция, порядок, слайд, сетка,
  камера, masonry остаются как есть (часть из них уже оптимистична по-своему).
  Переименование, перемещение, создание — не сейчас (см. «Позже»).
- Каждый этап — отдельный коммит (коммитит пользователь), тесты зелёные, ручная проверка в вебе.

## Как устроено сейчас (то, на что опирается план)

**Навигация.** `navigate()` ([navigation.ts:308](apps/client/src/store/explorer/navigation.ts))
ждёт `show()` целиком и только потом `push()`. Пока ждёт — на экране старая папка.
`navigating` читает только вотч в [FolderContent.vue:47](apps/client/src/ui/explorer/FolderContent.vue).
`use_folder_place` уже прячет стор, пока `opened_folder_id` не совпал с `location`
([use_folder_place.ts:64](apps/client/src/ui/explorer/folder-header/use_folder_place.ts)).
Шапка уже берёт имя из пути (`bookmarks.ts:84`, `folder_header.ts:49`).

Первое открытие облачного корня (стора ещё нет; повторный заход в тот же корень берёт
стор из карты, `drives.ts:181`) ждёт по очереди:
1. `cloud_roots()` ([drives.ts:361](apps/client/src/store/explorer/drives.ts)) — список воркспейсов
   и `workspace_root_info` (два select по `entries` для всех корней), хотя `load_store`
   берёт оттуда только имя.
2. `get_workspace_access` (два select: `workspaces`, `workspace_members`) — заодно решает
   «нет сети / нет доступа» ([openWorkspaceStore.ts:49](apps/client/src/store/helpers/openWorkspaceStore.ts)).
3. `createWorkspaceStore`: RPC `folder_read('/')` (до `try`, его ошибка уходит в
   `cloud_failure_message`) и `start_watching` корня — ждёт `SUBSCRIBED` канала `entries`;
   ошибка подписки сообщается, стор открывается без неё (`createWorkspaceStore.ts:529`).
  Стор кладётся в карту `drives` ещё до `adopt` (`drives.ts:196`).
4. `drives.open` **до** чтения цели меняет `current_root_id/current_drive_id`, делает
   `adopt` и `sweep()` — тот может уже уничтожить прежний стор (`drives.ts:126`, `:216`).
5. `navigate_open_folder(цель)`: `folder_read`, затем ждёт `prefetch_preview_folders`,
   `start_watching` цели и `expand_folder_in_sidebar` (предки по одному). Чернила и
   связи уже идут фоном. Поколения у самого открытия нет: медленное открытие B может
   закончиться после быстрого C и вернуть стор в B (`createWorkspaceStore.ts:849`).
   Прямые чтения (здесь, в конструкторе, `ensure_preview_folder`, `show_folder_children`)
   не накладывают `apply_pending_entry_xattrs` — это делают `refresh_cached_folder` и
   `reload_folder_cache` (`createWorkspaceStore.ts:1633`). `refresh_cached_folder` сразу
   выходит, если папки ещё нет в `store.folders` (`refreshCachedFolder.ts:100`).

После `push` `Sidebar.vue:227` ещё раз зовёт `cloud_roots()` и обход дерева (`tree.ts:309`).
Во время перехода старым стором пользуются дроп файлов (`AppShell.vue:93`) и действия
в верхней панели (`TopBar.vue:98`).

**Изменения вида папки.** `persist_xattr` ([xattrs.ts:259](apps/client/src/services/workspace/xattrs.ts))
меняет стор **после** `fm.set_xattr`. Вид, иконка, цвет-обложка ждут запись атрибута;
обложка и фон картинкой ждут ещё и `sweep_pile_images` (в `set_xattr` и `remove_xattr`,
только для `cover`/`background`). Плитку на открытой доске и строку дерева обновляет
`mirror_to_listings` (`createWorkspaceStore.ts:172`), корень на странице «Облако» —
`note_cloud_root_look` (`cloud.ts:333`); оба вызываются только после успеха.
`fetch_root_look` / `refresh_root_look` (`cloud.ts:679`, `:688`) заменяют `cloud.root_look`
целиком. Закрытый корень в дереве берёт вид из `DriveRoot.view` (`TreeRow.vue:132`).
Позиция и порядок детей стор меняют до записи — их новый откат не касается.
Защита от устаревших чтений (`pending_entry_xattrs`, поколения папок, `xattrs.ts:121`)
глобальная и ключуется только путём; `/` общий у всех корней. Наложение живёт 2 с
после записи (`xattrs.ts:297`).
`remove_xattr` в облаке — чтение-изменение-запись всего JSON `xattrs` (`supabase.ts:1448`):
параллельная запись другого ключа той же записи может потеряться. `merge_entry_xattrs`
атомарна, но умеет только ставить строки, не удалять ключ.

**Обложка картинкой.** [choosePileImage.ts](apps/client/src/services/workspace/choosePileImage.ts):
выбор → webp (2048 px) → `write_pile_image` (внутри считает `hash8`) → токен
`pile:cover-<hash8>.webp` → `change_folder_cover` → показ. Хеш зависит только от байтов,
поэтому токен можно знать **до** заливки. `seed_pile_url` показывает свои байты без
скачивания, но: сид живёт с `refs: 0` и отзывается, как только плитка ушла; ключ сида
`${folder_id}\0${token}`: обычная доска строит ключ без воркспейса, страница «Облако» —
с ним (`useResolvedFill.ts:42`); при уже идущей загрузке по ключу сид ничего не делает.
`sweep_pile_images` один раз читает атрибут и удаляет остальные файлы роли. Это гонка
уже сегодня: повторный выбор ничем не заблокирован (`begin_pile_image` только считает),
а другое устройство о чистке не знает — свежий файл чужой или следующей обложки может
быть удалён до записи его атрибута.

**Кеш картинок.** Только в памяти, по ссылкам: ушла последняя плитка — blob отозван.

**Бэкенд.** Токен проверяется локально (ES256, JWKS кешируется глобально). `POST /presign/upload`:
`require_write_access` → `assert_owner_quota` → `register_upload` (replace-запроса у
обложки нет). `POST /finalize` ([uploads.ts:36](apps/backend/src/uploads.ts)): `prepare_upload`
дважды → HEAD staging → поток GET+PUT **через бэкенд во Франкфурте** (B2 в Вирджинии)
→ HEAD final → `complete_upload`. `GET /presign` идёт через `download_target`
(security definer: членство, превью, `allow_download`, корзина), по нему выбирается
превью и пишется egress.

### Этап A. Удаление атрибута не стирает соседние (баг 2.6.0)

Найден на ревью 2, исправляем по решению пользователя (2026-11-04). Сейчас `remove_xattr`
в облаке читает весь JSON `xattrs`, удаляет ключ и записывает JSON целиком
(`supabase.ts:1448`). Если в это время другой клиент или синк (`syncPass.ts:915`) записал
соседний ключ той же записи, его изменение пропадает.

- База (forward diff, единственное изменение схемы в плане): `create or replace function
  private.merge_entry_xattrs` — значение `null` у ключа означает «удалить ключ».
  Проверка значений пропускает `string` и `null`; запись — `(xattrs || строки) - ключи
  с null`; лимит 64 КБ считается по результату. Сигнатура та же, `public`-обёртка и
  права не меняются. Старые клиенты `null` не шлют (сейчас он отвергается) — изменение
  совместимо.
- Клиент: `remove_xattr` идёт через `merge_xattrs` с `null`, одним запросом без
  предварительного чтения; чистка картинок после него — как решит этап 2b.
- Порядок по `AGENTS.md`: тест в `rls.test.sql` (удаление ключа не трогает соседние;
  `null` и строка в одном вызове; лимит), `postgres.test.ts` локально → diff в прод через
  `apply_migration` с согласия пользователя → `test:rls:remote` → `get_advisors` →
  только потом клиент. `rpc.sql` — зеркало итогового состояния.

Проверка: SQL-тесты выше; vitest на `remove_xattr` (один вызов RPC, без select);
вручную — синк папки, где одновременно меняется и удаляется атрибут.

### Этап 1a. Переход в папку откликается сразу

Для пользователя: клик по облачной папке — сразу её шапка (имя, путь) и заготовка
содержимого (серые плитки, как в Google Drive). Содержимое появляется, как только пришло.
Не открылась — остаёмся там, где были, ошибка как сейчас. Вид заготовки пользователь
выбирает по живому варианту: заготовка или пустое поле с индикатором в шапке.

Устройство — **`location` не трогаем раньше времени**. Ранний `location` ломает контент,
снимок выделения, историю, `public_view.go_to`, дерево (см. ревью 1). Вместо этого:
- В навигации появляется `target`: цель перехода, пока `show()` в полёте (ставится сразу,
  снимается при успехе вместе с `push`, при ошибке и при отмене).
- Шапка и крошки показывают `target ?? location` (имя из пути — как сейчас).
- `target` и заготовка — только для облачных и публичных целей: там переход всегда
  идёт в сеть (≥ 0,3 с), мигать нечему. Заготовка ставится **сразу**, старое содержимое
  размонтируется — вместе с ним снимаются все его обработчики на `window` (Delete,
  F2, инструменты холста и прочие). Локальные диски — как сейчас, без `target`.
- `location`, история, снимок выделения, предок для выделения, `open_folder` и его
  контракт «резолвится, когда стор совпал с целью» — без изменений.
- «Назад» во время перехода — отмена: `cancel()` и остаёмся на `location`.
- Поколение открытия внутри стора: `navigate_open_folder` применяет результат
  (`folders`, `opened_folder_id`) только если его не обогнало более новое открытие
  или отмена. Поколение общее с вкладками (`createWorkspaceStore.ts:735`–`758`).
  Проигравшее открытие не должно выглядеть успехом, иначе `show()` сделает `push`.
  Но не через отклонение промиса: `open_folder` зовут без обработки ошибок вкладки,

  (`cloudFileManager.ts:94`), заливка допишет атрибут и без живого стора. Очередь 2a
  при `dispose` ничего не отменяет. Закрепить тестом: заливка → `dispose` → finalize →
  атрибут.
- В фоне: заливка файла, затем запись атрибута (через очередь 2a) — другие устройства
  никогда не видят токен без файла.
- Пометка «загружается» (`PileImagePending`).
- Ошибка: прежняя обложка, сообщение.
- Новый выбор во время заливки: побеждает последний. Предыдущая заливка атрибут не пишет
  (поколение на ключ), её файл уберёт чистка.
- Чистка с отсрочкой: удаляются только файлы роли, которые не названы в атрибуте **и**
  старше часа. Час отсчитывается по серверным временам, не по часам клиента: от
  `updated_at` самой папки (его ставит сервер при записи атрибута, `schema.sql:968`) до
  `updated_at` файла. Свежий файл — чужого устройства, синка или следующей обложки — не
  трогаем; его уберёт следующая чистка. Чистка не ждётся (`set_xattr`/`remove_xattr` её
  больше не await-ят) и идёт так и в пакетном `set_xattrs`. Схему не меняем.
  Цена: старая обложка ещё час лежит в `.pile` — попадает в экспорт (`pack.ts:89`) и
  квоту; синк лишний файл не трогает (`reconcile.ts:331`).
- Повторный выбор прежней картинки: `write_pile_image` находит готовый файл и сразу
  возвращает его токен (`supabase.ts:1145`), не трогая `updated_at` — старый неназванный
  файл чистка может удалить до записи атрибута. В этом случае «освежаем» файл пустым
  `merge_entry_xattrs` (любой `UPDATE` двигает `updated_at`, `schema.sql:968`) — один
  запрос и только при повторном выборе. Защищает и от чистки на других устройствах.
- Остаточный риск (принимаем): чтение списка и удаление в чистке неатомарны. Если
  другое устройство освежит и назовёт старый файл в ту секунду, пока идёт чистка, файл
  может пропасть. И пока старые версии приложения в ходу, их чистка остаётся
  немедленной. Полностью закрывает только условное удаление на сервере («удалить, если
  не назван и старше часа» одной операцией) — в «Позже».
- Закрытие вкладки или окна при незавершённых фоновых записях — предупреждение
  (`beforeunload` в вебе, запрос на закрытие окна в десктопе). Решение пользователя.
