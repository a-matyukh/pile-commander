# Этап 2: двусторонняя синхронизация (как обещано на /vision)

## Context

Этап 1 в ветке `feature/local-auto-sync` готов и проверен: локальная папка → облачная копия, замена бинарника на месте
(`replace_blob_entry`), обновление картинок на доске. Облачные правки (веб, соавторы, другой компьютер) на диск не приходят.
Цель — «Changes travel both ways on their own, and on either side the folder is still a board or a canvas».

Решения пользователя:
- конфликт (правка на обеих сторонах): **облачная версия остаётся под именем**, локальная правка становится
  `name (conflicted copy …)` на обеих сторонах;
- **несколько компьютеров сразу**: у облачного workspace пункт «Sync to a folder on this computer»;
- удалено в облаке → локальный файл **в системную корзину**, массовое удаление — пауза и вопрос;
- работаем дальше в этой ветке, без вливания в `main`. **Изменений БД не нужно**: всё на текущей схеме.

## Архитектура (одна модель, без event-driven применения)

Один движок на связанную папку, проходы сериализованы, каждый проход — трёхсторонняя сверка base / диск / облако в
**обе** стороны. Realtime и файловый watcher только **запускают** проход, сами ничего не применяют — это убирает
проблемы потерянных событий удаления, порядка событий и эха. После прохода base содержит состояние обеих сторон *после*
наших записей (stat файла после записи, облачная строка после чтения), поэтому проход, разбуженный нашим же эхом,
ничего не находит.

**Облачный снимок за проход — 3 постраничных запроса** (новые хелперы в `packages/file-manager/src/supabase.ts` рядом с
`list_workspace_entries`): `list_workspace_strokes(client, ws)`, `list_workspace_connections(client, ws)`
(концы связей — uuid записей, переводим в relative по листингу entries). Без запросов на каждую папку.

**Когда идём в облако:** при старте, после Realtime-события, раз в 5 мин и по «Sync now». Если нет ни локальных
изменений, ни облачного сигнала — проход по-прежнему без сети. Подписка: новый `watch_workspace(on_change)` у
`CloudFileManager` — слушатель на трёх уже общих каналах (entries, folder_strokes, folder_connections) этого FM;
сигнал = «облако грязное», проход через debounce.

## Правила для записей (reconcile, расширение текущего)

Добавляются действия: `download`, `download_folder`, `local_move`, `local_trash`, `local_conflict`.

| диск vs base | облако vs base | действие |
| --- | --- | --- |
| не менялся | новый / изменён | скачать (`download`, папки `download_folder`) |
| не менялся | переименован/перемещён (тот же `cloud_id`, другой путь) | `local_move` через `local_fm.rename/move` (он же перестраивает `.pile/connections.json`) |
| не менялся | удалён | `local_trash` (системная корзина, путь строго внутри корня) |
| изменён | не менялся | как сейчас: update / replace |
| изменён | изменён | `local_conflict`: локальный файл переименовать в `conflicted copy`, залить его как новый, облачную версию скачать под исходным именем |
| удалён | изменён | скачать обратно (раньше было `forget`) |
| удалён | удалён | забыть |
| новый с обеих сторон, одинаковый размер | — | adopt; разный — `local_conflict` |

Безопасность: порог массового удаления считается **отдельно для каждой стороны** (≥20 и больше половины → пауза);
`local_trash` проверяет, что путь внутри корня, до вызова `trash_path`; один облачный workspace — одна папка на
устройстве (`link_folder` отказывает, если ссылка на этот workspace уже есть).

**Запись на диск** — новый `LocalWriter` в `SyncPassDeps` (реализация в `store/localSync.ts` на plugin-fs/xattrs/
`invoke('trash_path')`, фейк в тестах): атомарно — временный файл в `<папка>/.pile/` (watcher и листинги его не видят)
→ `rename` поверх цели → вернуть xattrs (rename теряет их) → `stat` для base. Текст — тем же путём.

## Раскладка в обе стороны (layout)

- **xattrs** — base хранит сами записи (не хеши): `entries[rel].xattrs`. Слияние по ключам: изменился только у нас →
  в облако; только в облаке → на диск; на обеих → облако. Это переход формата `sync.json` **v1 → v2**: у v1 нет
  записей — первый проход v2 считает базой локальные значения (как первый пуш этапа 1).
- **Штрихи** — карта id в base на папку: `layout[F].strokes: { [cloud_id]: { local_id, hash } }`. Свои новые штрихи
  получают `derived_uuid`, пришедшие из облака хранятся локально под облачным id (без повторного хеширования —
  иначе рисунок дублируется каждый цикл). Трёхстороннее слияние по `cloud_id`, при двойной правке — облако.
- **Связи** — ключ, одинаковый для обеих сторон: `from_rel|from_handle|to_rel|to_handle`; значение — пропсы.
  На диск пишем абсолютные локальные пути и локальный детерминированный id (тогда «лечение» в `list_connections` —
  no-op и не будит watcher), в облако — облачные пути и облачный id.

## Решения по замечаниям Cursor (раздел ниже)

Принято как есть: stat последним (после rename и xattrs); перечитывать облачные строки после своих записей (уже
делает `refresh`); раскладку сверять в каждом проходе, который сходил в облако; каталоги до файлов, в корзину только
самый верхний удалённый каталог, корень и `.pile` — никогда; отдельное действие конфликта «облако держит имя» с
порядком rename → download → upload, уникальное имя копии; засев карты штрихов из v1 через
`derived_uuid(workspace_id, local_id)`; трёхстороннее удаление штрихов и связей; связи на диск — абсолютные пути +
локальный детерминированный id; приём v1 в `parse_sync_state` с подъёмом до v2 в памяти; второй компьютер — только
пустой каталог, без `adopt_before`, карта штрихов не засевается; `watch_workspace` сам поднимает каналы; две разные
паузы массового удаления (`mass_delete_cloud` / `mass_delete_local`) с разными текстами и подтверждениями;
переписать «Phase 2» в `LOCAL_SYNC.md` на шаге 6.

Иначе, чем предложено:
- **Сохранение base в ходе прохода** — не после каждой записи (тысячи перезаписей `sync.json` на первой загрузке),
  а не чаще раза в 2 с и в конце. Новые скачанные файлы после обрыва и так adopt-ятся по размеру; узкое окно
  остаётся только для перезаписи существующего файла.
- **Гонка с открытой доской за sidecar** — общий file manager не помогает (у sidecar-хранилища нет блокировок и
  внутри одного экземпляра). Вместо этого: после записи sidecar перечитать его и класть в base только те штрихи и
  связи, которые реально на диске. Затёртый доской штрих следующий проход скачает снова, а не сочтёт локальным
  удалением (иначе стёрли бы его в облаке).
- **Раскладку читать после действий над записями** (после `local_move` и загрузок), а не в начале прохода; ранний
  снимок нужен только для проверки «есть ли что делать без сети».

### Эхо

Проход после своего прохода пуст только если base уже записан до следующего `run()`. Движок это умеет: `again` планируется после `save_state`. Значит base обязан включать результат записи, а не состояние до неё.

- После загрузки файла в base кладутся stat **после** восстановления xattrs и `content_modified_at` строки **после** записи. На macOS `setxattr` двигает mtime. Если записать старый stat, следующий проход увидит локальную правку и зальёт файл обратно.
- Свой `replace` и сохранение текста двигают `content_modified_at`. Без повторного чтения строки следующий проход решит, что облако изменилось, и скачает файл обратно.
- `set_xattrs` двигает `updated_at`, но не `content_modified_at` (так устроен `entries_touch` для уже существующего блоба). Перенос карточки в вебе — это xattr, не правка файла. Сверка записей, которая по-прежнему смотрит только `content_modified_at`, файл не скачает и не должна. Раскладку нужно сверять в каждом проходе, который уже сходил в облако, даже если действий над записями нет.
- Фильтр `updated_by_client` — оптимизация одного события, не замена base. Своё эхо и так ничего не найдёт. Чужое событие в том же проходе пропускать нельзя.
- Запись `strokes.json` / `connections.json` будит watcher: `is_sync_state_path` игнорирует только `sync.json` и `sync.json.tmp`. Это нормально, если хеши раскладки в base уже новые. Временный файл в `.pile` тоже будит watcher (листинг `.pile` пропускает, так что в облако он не попадёт).
- Обрыв посередине прохода опаснее, чем в этапе 1. Сейчас state пишется один раз в конце. Скачанный файл при следующем запуске выглядит как правка с обеих сторон и станет conflicted copy самого себя. Base стоит сохранять после каждой успешной записи на диск и после каждой успешной записи в облако.

### Порядок записей на диск

- Сначала каталоги, внутри них файлы. В корзину уходит самый верхний удалённый каталог, не он и каждый его потомок по отдельности. Корень синхронизации и `.pile` не удаляются. `local_trash` по-прежнему проверяет, что путь внутри корня.
- Порядок из плана верный: временный файл в `.pile` → `rename` поверх цели → вернуть xattrs → stat последним. Stat раньше xattrs — ложная локальная правка.
- `local_fm.rename` / `move` сами переписывают `.pile/connections.json`. После `local_move` base раскладки этой папки нужно перечитать, иначе следующий проход решит, что связи изменились локально, и зальёт их в облако.
- Конфликт этапа 1 другой: локальная копия уходит в облако под новым именем, и ссылка **переходит на копию**. Здесь ссылка исходного пути остаётся на облачной версии, а переименованный файл заливается как новая запись. Действие `conflict` переиспользовать нельзя.
- Порядок конфликта: переименовать локальный файл → скачать облачную версию под исходным именем → залить переименованный файл. Имя conflicted copy может уже существовать.

### Раскладка

- v1 хранит хеши, не карту штрихов. Первый проход v2 не может считать «все облачные штрихи новыми»: они уже залиты как `derived_uuid(workspace_id, local_id)`. Иначе каждый штрих появится на диске второй копией с облачным id. Перед слиянием карта строится из локальных id: `cloud_id = derived_uuid(...)`, хеш — от текущего штриха. Уже известные id из облака не скачиваются. Новые облачные id пишутся на диск под этим же id, без повторного `derived_uuid`.
- Удаление штриха в плане не названо. Нужны те же три стороны: удалён только в облаке → стереть локально; только локально → стереть в облаке; с обеих → забыть. Иначе стёртый в вебе штрих останется на доске навсегда.
- Двойная правка одного штриха — облако, как в плане. Правка позиции и удаление на другой стороне — тоже облако (удаление побеждает, если в облаке штриха нет).
- Связи: ключ `from_rel|handle|to_rel|handle` с обеих сторон совпадает, это верно. На диск — абсолютные пути под папкой и детерминированный id `` `${from}:${handle}-${to}:${handle}` ``. Тогда `list_connections` (`resolve_folder_connections`) не переписывает sidecar и не будит watcher. Относительный путь или чужой id как раз запускают это «лечение».
- Свойства связи при двойной правке — облако, включая удаление. Связь только локальная заливается, только облачная скачивается.
- xattrs: первый проход v2 с базой «как локально» правильно стянет облачные ключи, которых на диске нет, и отдаст облаку победу там, где значения разошлись. Это то, что нужно после этапа 1, который облачные xattrs не тянул. В `sync.json` лягут сами значения; у записей есть потолок 64 КБ, файл состояния вырастет, это приемлемо.
- Открытая доска держит штрихи в памяти и пишет sidecar сама. `LocalWriter` через plugin-fs с ней не сериализован: доска может записать старый снимок поверх скачанного. Пока папка открыта в окне, sidecar лучше писать тем же локальным file manager, которым пользуется окно, либо не писать sidecar, пока в этой папке есть несохранённый жест.

### sync.json v1 → v2

`parse_sync_state` сейчас возвращает `null` при `version !== 1`. Для движка это «папка не связана»: синк встаёт, ничего не заливая. Миграция обязана принимать v1 и поднимать его в памяти до записи v2. Отказ от v1 выглядит как отвязанная папка; повторный `link_folder` создаст пустой base и начнёт adopt/upload заново.

Проверки `root_path`, `device_id`, `user_id`, `workspace_id` остаются. Скопированная на другой компьютер папка вместе с `sync.json` по-прежнему не должна литься в тот же workspace.

Поля v1, которых нет в v2 (`xattrs_hash`, `strokes_hash`, `connections_hash`), после миграции не читаются. `exclude` и `adopt_before` сохраняются.

### Второй компьютер

- Пункт меню создаёт **пустой** каталог. Непустой нельзя брать как «пустой base»: одинаковый размер даст adopt без сравнения байтов (хеша в схеме нет), разный — конфликт. `adopt_before` на такой загрузке не ставить.
- `device_id` у нового `sync.json` — этот компьютер. Общий только облачный workspace.
- Одна папка на workspace проверяется по `local_sync_links` этого устройства, не по базе. Второй компьютер от этого не страдает. Папка в iCloud/Dropbox, открытая на двух машинах сразу, планом не покрыта: оба движка будут писать одни и те же файлы.
- Первый снимок второго компьютера — только скачивание. Карту штрихов засеивать `derived_uuid` не из чего: локальных id ещё нет, облачные id пишутся как есть. Иначе штрихи первого компьютера задвоятся.
- Дальше штрих, нарисованный на втором компьютере, приходит на первый как неизвестный `cloud_id` и хранится под ним. Ответный штрих первого уходит как `derived_uuid` и на втором тоже хранится под облачным id. Повторного хеширования ни там, ни там нет.
- Каналы Realtime в `supabase.ts` поднимаются лениво, когда у папки появляется watcher. `watch_workspace` должен подписаться сам, даже если ни одна папка workspace в окне не открыта. Иначе облачный сигнал не придёт, пока пользователь не откроет доску, и останется только пятиминутный интервал.
- Порог массового удаления на диске — отдельная пауза от облачной. Сейчас у движка один `reason: 'mass_delete'` и текст про файлы, пропавшие из папки. Подтверждение не должно отправить в облачную корзину то, что спрашивали про корзину macOS, и наоборот.

## Замечания Cursor, второй круг

Остальное из «Решений» учтено верно, включая приём v1, засев карты штрихов, две паузы и пустой каталог на втором компьютере. Ниже только три места, где решение иное. Код не менялся.

При подъёме v1 в v2 вместе с записями нужно сохранить `exclude` и `adopt_before`. В списке «принято» их нет.

### Сохранение base раз в 2 секунды

Для пачки новых скачанных файлов это верно. Обрыв до `rename` оставляет старый файл или ничего (временный файл в `.pile` листинг не видит). Обрыв после `rename`, пока пути ещё нет в `sync.json`: на диске и в облаке файл новый и того же размера → adopt, второй копии не будет. Итоговый state прохода всё равно пишется в конце целиком; раз в 2 секунды — только промежуточная запись. В памяти base обновляется сразу, иначе эхо внутри того же прохода увидит старое.

Формула «окно остаётся только для перезаписи существующего файла» узкая.

- Перезапись существующего — да, conflicted copy тех же байт. Терпимо. Adopt после обрыва должен взять `content_modified_at` из текущего листинга, не из недописанного base.
- `local_move` в эти 2 секунды — нет. `rename` и перепись `connections.json` меняют mtime, а сверка этапа 1 считает облако неизменным, если не изменился `content_modified_at`, и путь не смотрит. На диске файл уже по новому пути, в base — по старому, в облаке — по новому. Пара size+mtime не совпадёт, старый путь уйдёт в облачную корзину, новый зальётся заново, id сменится. То же окно у `local_trash` безопасно (локально нет, в облаке нет → забыть). Промежуточно сохранять base сразу после переноса и удаления, а не реже 2 секунд. Реже — только для скачивания и заливки содержимого.

### Sidecar после записи

Общий file manager действительно не помогает: `createLocalSidecarStore` делает read-modify-write без замка и внутри одного экземпляра. Перечитать файл и не считать затёртый штрих локальным удалением — правильная замена.

В base кладётся пересечение «что эта запись только что написала» и «что прочиталось», а не весь sidecar. Штрих, который доска дописала сверху, в base не входит: иначе у него уже есть `cloud_id` и следующий проход не зальёт его.

Перечитывание не видит запись доски, которая случилась после него. Тогда в base штрих есть, на диске его уже нет, в облаке он есть и не менялся → проход сотрёт его в облаке. Это как раз тот исход, которого решение избегает, только на шаг позже. Если mtime sidecar новее нашей записи, пропавшие относительно base штрихи и связи в облаке не удалять: докачать их на диск (облако побеждает, пока файл меняли не мы).

### Раскладка после действий над записями

Так и нужно. `local_move` переписывает `connections.json` уже после раннего снимка; в base и в слияние идёт только поздний снимок. Ранний служит лишь проверке «есть ли локальные изменения без сети» и в base не пишется.

Поздний снимок — все папки прохода, не только те, что скачали или перенесли. Иначе не приедут штрих и перенос карточки: у файла `content_modified_at` тот же, действий над записями нет, а раскладка изменилась. Это не отменяет уже принятое «сверять раскладку в каждом проходе, который сходил в облако».

## Решения по второму кругу

- **v1 → v2** переносит `entries`, `exclude`, `adopt_before`, `last_synced_at`. Карта штрихов засевается перебором
  локальных штрихов: `cloud_id = derived_uuid(workspace_id, local_id)`; хеши v1 (один на весь список) для этого не нужны.
- **Промежуточное сохранение base.** В памяти base обновляется сразу после каждого действия. На диск:
  структурные действия (`local_move`, `local_trash`, облачные move/delete, конфликт) — сразу; скачивание и заливка
  содержимого — не чаще раза в 2 с; весь state — в конце прохода. Adopt после обрыва берёт `content_modified_at`
  из текущего листинга (так уже делает `refresh`). Замечание про mtime при `rename` неточно (`rename` не меняет
  mtime файла), но немедленное сохранение структурных действий дешёвое и снимает вопрос.
- **Sidecar.** В base раскладки — пересечение «что записали в этом проходе» и «что перечитали», плюс неизменённое
  из прежнего base; новые штрихи доски в base не попадают (их зальёт следующий проход).
  Запись доски *после* перечитывания: правило «sidecar новее нашей записи → не удалять в облаке, докачать» в общем
  виде ломает стирание (любой штрих, пришедший из облака, после стирания возвращался бы). Сужено: base хранит
  `downloaded_at` для штрихов и связей, скачанных на диск; если такой элемент пропал с диска **в течение 10 с** после
  скачивания, он считается затёртым гонкой и докачивается, а не удаляется в облаке. Гонка с доской — миллисекунды;
  стереть штрих в первые 10 с после появления можно повторно.
- **Поздний снимок раскладки** — по всем папкам прохода; ранний только для проверки «нужен ли проход без сети».

## Замечания Cursor, третий круг

Сужение до 10 секунд верное. Правило «sidecar новее нашей записи → докачать» действительно вернуло бы любой стёртый штрих, который когда-то пришёл из облака: стирание всегда новее скачивания. Так стирание с доски не дошло бы до облака. Окно это чинит.

При повторном докачивании внутри окна `downloaded_at` не двигать. Иначе каждое возвращение штриха начинает новые 10 секунд, и стирание в этом окне отодвигает его снова. Вторым стиранием штрих уходит, только если срок считается от первого скачивания.

Хеш штрихов в v1 — один хеш всего списка, в нём нет id. Засев карты — по-прежнему перебор локальных штрихов и `derived_uuid(workspace_id, local_id)`. Хеш v1 говорит лишь, что список с прошлого пуша не менялся.

## Решения по третьему кругу

- Принято: при повторном докачивании внутри 10-секундного окна `downloaded_at` **не сдвигается** — срок считается
  от первого скачивания, второе стирание доходит до облака.
- Принято: засев карты штрихов не опирается на хеши v1 (исправлено в «Решениях по второму кругу»).

План согласован; реализация — по шагам из «Порядок работы», коммит и ревью после каждого шага.
