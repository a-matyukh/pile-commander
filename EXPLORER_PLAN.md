# Новый интерфейс: план интеграции Эксплорера

Переносим интерфейс из Vue-прототипа (`/Users/amatyukh/Desktop/pile-commander-file-manager-vue`, [репозиторий](https://github.com/a-matyukh/pile-commander-file-manager-vue)) в `apps/client`. Новый интерфейс включается флагом и работает на настоящих хранилищах с первого дня.

Статус: **ревью Cursor от 27.10.2026 учтено** (`EXPLORER_PLAN_REVIEW.md`). Это рабочий чек-лист, галочки ставятся по ходу. Шаги этапа 0 можно начинать по порядку.

## Как развиваем продукт

С 28.10.2026 каждый шаг относится к одной из трёх категорий:

1. **Продуктовое видение и позиционирование.**
2. **Пользовательский опыт.**
3. **Оптимизация, производительность, баги.**

Пока у продукта нет платящих пользователей, работаем в категориях 1 и 2. Этот план — интеграция нового интерфейса, чтобы начать им пользоваться и понять реальную ценность. Пограничные случаи, редкие гонки и оптимизации записываем в `BACKLOG.md` и возвращаемся к ним только с реальными платящими пользователями. Исключение — критические баги, которые мешают обычной работе (как зависание на `~/Library`): их чиним сразу.

Критерий каждого шага: пользователь сам быстро проверяет его в приложении на простых общих сценариях.

## Как работаем

| Кто | Роль |
| --- | --- |
| Пользователь | Владелец продукта: принимает решения, проверяет десктоп на себе, пересылает сообщения между агентами и сам делает коммиты |
| Claude | Ведёт план. Простые шаги отдаёт Grok Bot и ревьюит их; шаги сложнее делает сам |
| Grok Bot | Простые шаги |
| Kimi | Один раз ревьюит сложные шаги Claude |

- **Ветка.** Вся работа идёт в одной ветке `feature/explorer`. В `main` попадает одним слиянием в конце этапа 4. Если ветка долго живёт, `main` вливается в неё, а не наоборот.
- **Шаг — это коммит.** Каждый пункт чек-листа заканчивается одним коммитом. Порядок такой:
  1. Исполнитель реализует шаг, проходит проверки из раздела «Проверки», проверяет в браузере и оставляет изменения незакоммиченными.
  2. Ревью — **один раунд**. Исправляем то, что мешает обычной работе; остальное записываем в `BACKLOG.md`.
  3. Пользователь проверяет десктоп и сам делает коммит.

  Агенты не коммитят, не пушат и не сливают ветки. Следующий шаг начинается только после коммита предыдущего.
- **Ревью.** Ревьюер проверяет изменения по коду, а не по описанию. Замечания пишутся так, чтобы исполнитель мог их выполнить без этого чата: файл, строка, сценарий. Редкие пограничные случаи отмечаются как кандидаты в бэклог.
- **Вопросы.** Если план расходится с кодом, исполнитель не угадывает, а записывает вопрос в раздел «Открытые вопросы» и останавливается на этом шаге.

## Что решено

Источник решений: обсуждение прототипа с пользователем 26–27.10.2026.

### Модель для пользователя

- Пользователь видит три абстракции: **файл, папка, закладка**. Закладкой может быть любая папка с любого диска.
- Рабочих пространств, рабочих столов, окон и вкладок в интерфейсе больше нет. Вкладки заменяют закладки.
- Приложение показывает весь `~` и всё облако. Чтение ленивое, как сейчас: читается только открытая или раскрытая в дереве папка.
- Облачное рабочее пространство в интерфейсе выглядит как папка верхнего уровня в облаке. Она же остаётся единицей шаринга, публикации и Хаба.

### Внешний вид

- Дизайн, раскладку, меню и палитру берём из прототипа, а не из текущего Nuxt UI.
- Меню и диалоги собираются на «голых» примитивах Reka UI со стилями прототипа. Nuxt UI в новом интерфейсе не используется. Старые экраны работают на нём, пока их не удалят.
- Иконки — Tabler через уже существующий офлайн-плагин иконок продукта.
- Виды папок по умолчанию строятся на существующих реализациях продукта (`ui/workspace/folder-container/*`), а из прототипа берутся рамка вокруг вида и меню. Отдельные идеи прототипа могут лечь в текущие виды, а какой-то вид прототипа может целиком заменить текущий (например, список). Это решается по каждому виду на его шаге этапа 3.
- Порядок видов: список, галерея, доска, холст, стопка, мозаика, слайды. Дашборда нет.
- Вид `grid` переименовывается в `gallery` (см. «Совместимость данных»). «Сетка» теперь означает только сетку привязки на фоне доски и холста.

### Поведение

- **Последнее место.** При запуске открывается папка, открытая перед выходом. Если её нет, открывается корень её диска. Историю последних папок сохраняем, но списком пока не показываем.
- **Корзина.** Локальная кнопка открывает системную корзину в Finder. Облачная корзина — страница в Эксплорере, у каждой облачной папки верхнего уровня своя (`cloud.fetch_trash(workspace_id)`, сейчас в `ui/workspace/sidebar/TrashDialog.vue`). Удаление локальных файлов и папок в новом интерфейсе — это «Переместить в корзину» в корзину ОС, как в Finder. Сейчас приложение удаляет их безвозвратно: `factory.ts` не передаёт `remove_to_trash`, хотя `local.ts` его умеет. В корзину ОС пишет только синхронизация (`trash_path`).
- **Публичные ссылки** (`/demo`, `/<user>/<slug>`) открываются как папка только для чтения в Эксплорере. Профиль `/<username>` и приглашение `/invite/<token>` — не папки, а страницы Эксплорера. Все маршруты уже разбирает `services/publicRoute.ts`.
- **Перетаскивание папки из ОС.** Брошенная на верхнюю панель папка добавляется в закладки, брошенная в любое другое место — открывается.
- **Перетаскивание в дереве** перемещает папку в другую папку. Ручная сортировка в дереве и поиск папок отложены.
- **Настройки.** Все эксперименты из настроек прототипа остаются. Пользователь сам потом решит, что убрать.
- **Веб-версия.** Вместо `~` там диск «Локальное хранилище браузера» (IndexedDB), плюс облако и Хаб.
- **Язык.** Интерфейс на русском и английском, по умолчанию язык системы. Переключатель в настройках.

## Архитектура

### Что не меняется

- `FileManager` из `packages/file-manager` — интерфейс бэкенда с реализациями `local`, `browser`, `cloud`, `demo`, `fake`. Новый интерфейс файловой системы не вводим. `FileSource` из прототипа заменяется на `FileManager` и `WorkspaceStore`.
- `WorkspaceStore` — хранилище одного корня: дерево, кэши, вотчер, `can_write`, `live`, вкладки. Меняется только вотчер (см. «Граница локального стора»). Вкладки стора не трогаем: Эксплорер пользуется одной.
- `open_workspace_store` (`store/helpers/openWorkspaceStore.ts`) — выбор `FileManager` по типу и проверка доступа. Логика не меняется, её вызывает Drive.

### Новое: Drive

Drive стоит над `WorkspaceStore` и собирает корни под одним пунктом в панели источников. Он нужен из-за облака: там один `FileManager` и один `WorkspaceStore` на каждое облачное пространство (`create_app_cloud_file_manager(workspace_id)`), а пользователь видит одно «Облако» с папками внутри.

```ts
// apps/client/src/domain/Drive.ts

/** Today's WorkspaceType; S3 or a media server becomes one more kind */
type DriveKind = 'local' | 'browser' | 'cloud' | 'demo'

type Drive = {
	/** 'local', 'browser', 'cloud'; later 's3:<bucket>' */
	id: string
	kind: DriveKind
	/** «Этот Mac», «Локальное хранилище браузера», «Облако» */
	name: string
	icon: string

	/**
	 * Top-level folders of the drive in the tree:
	 * local — ~ plus folders opened outside it (/Volumes/…);
	 * browser — one virtual root; cloud — one per cloud workspace
	 */
	roots(): Promise<DriveRoot[]>

	/**
	 * The store that owns this root; opened on first use. Kept while the root
	 * is expanded in the tree or holds the current location, then disposed
	 */
	store_for(root_id: string): Promise<WorkspaceStore>

	/** Trash: a page in the Explorer, the system Trash (Finder), or none */
	trash: 'page' | 'system' | null
}

type DriveRoot = {
	id: string        // local: home path or a folder outside it; cloud: workspace UUID
	name: string
	can_write: boolean
}

/** Address of any folder: bookmarks, history and the last location store this */
type FolderRef = {
	drive_id: string
	root_id: string
	/**
	 * The folder id as WorkspaceStore uses it today: an absolute path
	 * locally, a path from "/" in the cloud. Not relative to the root
	 */
	folder_id: string
}
```

| Сейчас | Становится |
| --- | --- |
| `WorkspaceType` | `DriveKind` |
| `WorkspacesListItem` | `DriveRoot` + `FolderRef` |
| `open_workspace_store(item)` | внутренности `Drive.store_for(root_id)` |
| закладки и последние (`store/workspaces_list.ts`) | список `FolderRef` под новыми ключами хранения |

Слово «Workspace» в коде остаётся за `WorkspaceStore` и облачным пространством. В интерфейсе пользователь его не видит.

### Граница локального стора

Сегодня корень локального стора — выбранная пользователем папка. В новом интерфейсе корень — `~`, и это меняет три вещи.

- **Вотчер.** Сейчас `createWorkspaceStore` при создании ставит рекурсивный watch на корень (`store/createWorkspaceStore.ts`, `start_watching`, вызов в конце файла), а при открытии папки переносит его на открытую папку. Рекурсивный watch на весь `~` или целый внешний диск недопустим: туда постоянно пишут `~/Library`, кэши и другие программы.

  Стор общий для обоих интерфейсов, поэтому новая политика — опция `createWorkspaceStore`, которую включает только Drive. Без неё стор работает как сейчас: один слот `unwatch` и один рекурсивный watch на открытую папку, как у выбранной папки проекта в старом интерфейсе. С ней:
  - начальный watch ставится на открытую при запуске папку, а не на корень;
  - все watch нерекурсивные, и у открытой папки тоже, будь то корень (`~` или корень вне него, например `/Volumes/...`) или папка ниже. Рекурсивный watch на `~/Library` или папку с `node_modules` подвешивает приложение: поток событий FSEvents, а debounced-вотчер при старте обходит всё поддерево. Изменения в глубине видны при открытии: папка читается заново, когда её открывают;
  - каждая раскрытая в дереве папка, в том числе внутри открытой, получает свой нерекурсивный watch. Сворачивание папки его снимает. Так дерево видит новые, переименованные и удалённые папки из Finder и других программ в любой раскрытой ветке. Сегодня этого нет: watch уходит за открытой папкой, и раскрытые ветки вне неё не обновляются.

  Свёрнутые папки не отслеживаются: при раскрытии они всё равно читаются заново. Изменения, сделанные в самом приложении, попадают в дерево сразу, без вотчера. В облаке все watch идут через один realtime-канал (`fm.watch`), поэтому лишних подключений это не добавляет.
- **Экспорт, bridge и синхронизация.** Сейчас они берут `id` и `uid` стора как единицу (`export_current_workspace` в `store/index.ts`, `store/bridge.ts`). Домашняя папка такой единицей не становится. В новом интерфейсе эти действия получают папку, которую выбрал пользователь, а не корень стора. До шага 3.5 в новом интерфейсе их нет. Облачная единица остаётся UUID пространства.
- **Папки вне `~`.** Диалог открытия папки, перетаскивание из ОС и импорт `.pile` принимают любой путь, например `/Volumes/...`. Путь внутри `~` — папка корня `~`. Путь снаружи — отдельный `DriveRoot` локального диска со своим стором. Такой корень показывается в дереве, пока на него есть закладка или он — текущее место.

### Диск браузера

Хранилище браузера держит пути вида `/browser-desktops/<id>/…` (`packages/file-manager/src/browser/browser.ts`). Это пространства, созданные во времена рабочих столов; экрана, который создаёт новые, в клиенте нет. Корень диска «Локальное хранилище браузера» — виртуальная папка `/browser-desktops`, она создаётся, если её нет. Старые пространства показываются её подпапками. Их имена — id, поэтому до этапа 4 Эксплорер показывает имя из старого списка пространств (`workspaces_list`), а на шаге 4.2 папки переименовываются. Раньше переименовывать нельзя: старый интерфейс за выключенным флагом ищет их по старым путям.

### Жизнь сторов

- Текущий стор по-прежнему лежит в `store.workspace`: старые диалоги в `AppShell` продолжают с ним работать. Сейчас это геттер над `fullscreen_workspace` (`store/index.ts`), и для Drive нужен способ сделать стор текущим, не вызывая `dispose` у предыдущего.
- Навигация не вызывает `load_workspace` на каждый переход: он закрывает предыдущий стор и пишет старый список «последних».
- Drive держит стор, пока его корень раскрыт в дереве или в нём текущее место. Остальные он закрывает, иначе у каждого посещённого облачного пространства остаётся realtime-канал.

### История

- История назад/вперёд и выделение живут в `store/explorer/`, потому что история переходит между дисками и страницами.
- Переход в папку вызывает `open_folder(id, { skipHistory: true })` нужного стора. `go_back` стора не вызывается: у стора нет «вперёд», и его стек `folder_back_stack` не знает про другие сторы.

### Публичные ссылки и демо

`public_readonly` есть только у `open_workspace_store` (`store/helpers/openWorkspaceStore.ts`). Демо и `/<user>/<slug>` открываются отдельным входом в Drive: временный корень только для чтения, а не `store_for` корня «Облако».

### Состояние интерфейса

Как в прототипе: модули на `reactive`, настройки в `useStorage`, без Pinia, имена в `snake_case`. Новые модули лежат в своей папке `store/explorer/`.

## Совместимость данных

- **`grid` → `gallery`.** Переименовывается только значение вида. Ключи сетки привязки `snap_to_grid`, `grid_size` и `show_grid_dots` остаются как есть.
- **Значение вида.** На файлах и в облаке лежит `user.view = "grid"`. Установленные версии 2.2.x и участники облачных папок на старых версиях не поймут `gallery`, поэтому переход идёт в два шага:
  - до конца этапа 4 новый код читает оба значения (`grid` как `gallery`), а записывает `grid`;
  - после этапа 4 он по-прежнему читает оба значения, но записывает `gallery`.
- **Закладки и последние.** Старые списки в `localStorage` (`workspaces_list_bookmarks`, `workspaces_list_last_opened` в `store/workspaces_list.ts`) один раз переводятся в `FolderRef` под новыми ключами. В них лежат корни пространств, а не вложенные папки, поэтому первый запуск после переноса открывает корень. Пропавшие пути и удалённые облачные пространства при переносе отбрасываются, как это делает `sync_workspaces_list`. Старые ключи не удаляются до этапа 4, чтобы выключенный флаг возвращал прежнее поведение.
- **База данных.** План не требует изменений схемы. Если они понадобятся, действуют правила из `AGENTS.md`: только прямой дифф, никакого повторного применения `schema.sql` или `rpc.sql` целиком.

### Этап 1. Верхняя панель

- [x] 1.1. Назад, вперёд, кнопка сайдбара и горячие клавиши. Клавиши через `defineShortcuts`, как в `WorkspaceWindow.vue`: ⌘ на macOS и Alt на других системах, в десктопе и в вебе. ⌘B и ⌘← уже есть в приложении, ⌘→ — новая клавиша Эксплорера: у стора нет шага вперёд, его даёт история из `store/explorer/`. Отступ под светофор macOS и область перетаскивания окна (`data-tauri-drag-region`, см. `WorkspaceWindow.vue`).
- [x] 1.2. Панель закладок и выпадающий список закладок.
- [x] 1.3. Перетаскивание папки из ОС: на верхнюю панель — закладка, в остальное окно — открыть. Точку броска даёт Tauri, логика сейчас в `AppShell.vue` (`listenFolderDrop`). Остальное поведение сохраняется: файлы, брошенные в окно, попадают в открытую папку, `.pile` открывается, событие `opened-paths` (`listenOpenedPaths`) работает.

Готово, когда: по закладкам и истории можно ходить по реальным папкам, а содержимое показывается старым видом папки.

### Этап 2. Сайдбар

- [x] 2.1. Панель источников (диски, Хаб) и изменение ширины сайдбара.
- [x] 2.2. Дерево на `WorkspaceStore.tree`: только папки, файлов в дереве нет. Ленивое раскрытие, меню папки. Папки с точкой в начале имени показываются по существующей настройке `show_hidden_files` (`store/showHiddenFiles.ts`); второй переключатель не заводится.
- [x] 2.3. Панель фильтров и сортировки дерева. Сортировка по имени и по виду папки, по возрастанию и убыванию; без сортировки по дате (см. «Вне плана»).
- [x] 2.4. Перетаскивание в дереве = перемещение папки внутри одного стора.
- [x] 2.5. Перемещение между корнями одного диска (облачными пространствами; `~` и папками вне него) через `crossStoreTransfer` (`store/helpers/crossStoreTransfer.ts`). Между `~` и облаком — отложено (см. «Вне плана»).

Готово, когда: по всему `~` и облаку можно ходить только деревом.

### Этап 3. Эксплорер

- [x] 3.1. Шапка папки: хлебные крошки, подзаголовок, действия с папкой, выбор вида.
- [x] 3.2. Страницы: настройки (интерфейс, ИИ, другое, переключатель флага), аккаунт, Хаб, облачная корзина, профиль `/<username>`, приглашение `/invite/<token>`. Логика берётся из существующих диалогов (`AccountPanel`, `AuthForm`, `ProfileDialog`, `PasswordDialog`, `AiSettingsSection`), меняется только оболочка. Квота, bridge, пароль, диалоги ИИ и баннер обновления остаются в `AppShell` и на этом шаге не переезжают.
- [ ] 3.3. Рамка вокруг существующих видов и горячие клавиши навигации по элементам (стрелки, ⌘↑, ⌘↓). Виды внутри рамки остаются на Nuxt UI с английскими строками, пока их не сменит отдельный шаг.
- [ ] 3.4. Публичные ссылки и демо как папка только для чтения.
- [ ] 3.5. Синхронизация, шаринг, публикация, экспорт и bridge вокруг выбранной папки и облачной папки верхнего уровня.

Готово, когда: всё, что умеет старый интерфейс, доступно в новой рамке на текущих видах. Это условие перехода к этапу 4.

#### Виды

- [ ] 3.6–3.12. Виды по одному коммиту: список, галерея, доска, холст, стопка, мозаика, слайды. Перед каждым видом пользователь решает, что берём: текущую реализацию, её же с идеями прототипа или вид из прототипа целиком.

Работа над видами может идти и после этапа 4. Слияние в `main` её не ждёт.

### Этап 4. Переключение

- [ ] 4.1. Флаг включён по умолчанию, ручная проверка на десктопе и в вебе.
- [ ] 4.2. Удаление старого окна, вкладок, старого сайдбара и старых ключей хранения. Папки браузера `/browser-desktops/<id>` переименовываются в имена из старого списка пространств, пока он ещё есть.
- [ ] 4.3. Вид записывается как `gallery` вместо `grid`; чтение `grid` остаётся.
- [ ] 4.4. Слияние `feature/explorer` в `main`.


## Вне плана

- Дашборд.
- Ручная сортировка папок в дереве.
- Поиск папок и «Открыть в браузере» (в прототипе за флагами итерации).
- Перетаскивание между `~` и облаком: дерево показывает один диск за раз; нужны «пружинящие» кнопки источников и решение «переносить или копировать».
- Сортировка «По дате изменения»: ни один `FileManager` пока не отдаёт дату изменения. Добавляется вместе с другими отложенными функциями прототипа, по мере необходимости.
- Ярлыки на папки (беклог, конец ноября 2026).
- Вложенная синхронизация.
- Новые типы дисков (S3, медиасерверы): архитектура их допускает, но они не реализуются.
